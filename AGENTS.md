# PROJECT RULES: ЕООП «Школьник» / school-platform-v2

## 1. Цель проекта
Поэтапно перенести существующий функционал Flask/SQLite в новую платформу
FastAPI + React + PostgreSQL + Android/iOS без потери функций и данных,
а затем расширить её до республиканского уровня.

## 2. Технологический стек
- Backend: Python 3.12/3.13, FastAPI, SQLAlchemy 2.0 (async), Alembic, asyncpg.
- База данных: PostgreSQL 16+; Redis для кеша, очередей и сессий.
- Frontend: React 18+ + TypeScript, Vite, TailwindCSS, React Router, Axios.
- Mobile: Flutter (Dart), Android/iOS, локальное хранилище Hive/SQLite.
- AI: OpenRouter (DeepSeek и другие модели) через OpenAI-совместимый API.
- Файлы: S3-совместимое хранилище (MinIO в разработке, внешнее — в production).
- Документация: Markdown как источник, DOCX — официальные версии.

## 3. Критические правила
1. НЕ УДАЛЯЙ существующие функции и данные старого проекта, пока их эквивалент
   не реализован, не проверен и не принят.
2. Сначала анализируй старый код и фиксируй требования, затем предлагай
   эквивалент на FastAPI.
3. Не меняй схему БД без миграции Alembic.
4. Не коммить секреты, токены, пароли, реальные персональные данные.
5. Все персональные данные детей — только в согласованных защищённых полях,
   с аудитом доступа и минимально необходимым сроком хранения.
6. Любое изменение поведения API фиксируй в `docs/10-reporting/04-zhurnal-izmeneniy.md`.
7. Перед началом задачи читай `.opencode/memory-bank/activeContext.md`.
8. После завершения задачи обновляй `.opencode/memory-bank/progress.md`.

## 4. Архитектурные правила
- API-first: web, Android и iOS используют один и тот же API.
- Мультитенантность: данные школы изолируются по `school_id`; доступ проверяется
  на уровне API и, где возможно, на уровне PostgreSQL RLS.
- Мультиязычность: текстовые поля контента хранятся в JSONB
  `{"ru": "...", "by": "...", "en": "..."}`; интерфейс — через i18n.
- Асинхронность: только async-драйверы БД и async HTTP-клиенты.
- Идемпотентность: операции синхронизации и создания платежей/документов
  должны иметь idempotency key.
- Offline-first для мобильных клиентов: локальная очередь, повторная отправка,
  разрешение конфликтов по правилам, описанным в документации.
- Модульный монолит на старте; выделение сервисов — только при доказанной
  необходимости и без нарушения границ доменов.

## 5. Стандарты кода
- Python: PEP 8, Ruff, mypy (по возможности), Pydantic v2.
- TypeScript: strict mode, ESLint, функциональные компоненты и хуки.
- Flutter: null safety, разделение слоёв data/domain/presentation.
- Каждый новый эндпоинт сопровождается тестами pytest.
- Каждый новый экран — минимум одним widget-тестом или интеграционным сценарием.
- Публичные API документируются через OpenAPI/Swagger.

## 6. Документация и отчётность
- Официальные документы — в `docs/`, исходники — Markdown, версии — DOCX.
- Отчёты о разработке и тестировании ведутся по шаблонам из `docs/10-reporting/`.
- Все решения, отклонения и риски фиксируются в журналах.
- Перед сдачей этапа проверяется матрица соответствия требованиям.

## 7. Безопасность
- Пароли — только Argon2id или bcrypt с безопасными параметрами.
- JWT — короткоживущий access token + refresh token с ротацией.
- Все внешние вызовы — с таймаутами, retry и ограничением размера ответа.
- Загрузки файлов — проверка MIME, размера, антивирусная проверка на сервере.
- Логи не должны содержать пароли, токены, полные номера документов и лишние ПДн.
- Для production — HTTPS, WAF, rate limiting, резервное копирование, мониторинг.

## 8. Поведение агента
- Не начинай с написания всего проекта. Один шаг — одна проверяемая задача.
- Перед изменением файлов кратко опиши план.
- После изменений запускай релевантные тесты и показывай результат.
- Если требование неоднозначно — задай вопрос, не выбирай юридически значимое
  поведение самостоятельно.
- Не выполняй destructive-команды без явного подтверждения пользователя.
