# Стратегия тестирования

| Параметр | Значение |
|---|---|
| Код документа | ШК-06-01 |
| Версия | 0.1 |
| Статус | Черновик |
| Дата | 27.10.2026 |

## 1. Цели
- Подтвердить соответствие функций требованиям ТЗ.
- Обеспечить стабильность, безопасность и производительность.
- Предотвратить регрессии при миграции и развитии.
- Дать объективные данные для приёмки и аттестации.

## 2. Принципы
- Тестирование начинается с первых этапов, а не перед релизом.
- Автоматизация приоритетна для критичных сценариев.
- Каждый дефект имеет воспроизводимый сценарий.
- Тестовые данные не должны содержать реальные ПДн без обезличивания.
- Для каждой роли проверяются права доступа.
- Для офлайна проверяются худшие условия связи.

## 3. Уровни тестирования
| Уровень | Что проверяется | Кто |
|---|---|---|
| Модульное | Функции, сервисы, валидаторы | Разработчики |
| Интеграционное | API, БД, очереди, S3, AI-адаптеры | Разработчики/QA |
| Системное | Сквозные сценарии | QA |
| E2E | Web, Android, iOS | QA |
| Приёмочное | Требования ТЗ | Заказчик/QA |
| Нагрузочное | Пиковые нагрузки | QA/DevOps |
| Безопасность | Уязвимости, права, ПДн | ИБ/пентест |
| Доступность | a11y, контраст, screen readers | QA/UX |
| Совместимость | Браузеры, устройства, ОС | QA |

## 4. Виды тестирования
- Функциональное.
- Регрессионное.
- Дымовое.
- Интеграционное.
- API-контрактное.
- UI/UX.
- Кроссбраузерное и кроссплатформенное.
- Мобильное (Android/iOS).
- Офлайн и синхронизация.
- Производительность и нагрузка.
- Безопасность.
- Доступность.
- Локализация RU/BY/EN.
- Данные и миграция.
- Отказоустойчивость.
- AI-качество и безопасность контента.

## 5. Тестовые среды
| Среда | Назначение | Данные |
|---|---|---|
| Dev | Разработка | Синтетические |
| Test | Функциональные тесты | Синтетические |
| Stage | Приёмочные, нагрузочные | Обезличенные |
| Pilot | Опытная эксплуатация | Реальные с согласиями |
| Prod | Промышленная | Реальные |

## 6. Тестовые данные
- Генерация синтетических пользователей и классов.
- Обезличивание при переносе.
- Запрет реальных ПДн в Dev/Test.
- Отдельные наборы для 1–2, 3–4, 5–9, 10–11 классов.
- Данные для всех ролей и иерархий.
- Файлы: PDF, изображения, аудио, вредоносные образцы (в изолированной среде).

## 7. Матрица ролей и прав
Для каждой роли проверяется:
- доступ к своим данным;
- запрет на чужие данные;
- запрет на админские функции;
- корректность интерфейса при отсутствии прав;
- журналирование значимых действий.

Роли: ученик, родитель/опекун, учитель, директор/завуч, секретарь, методист,
психолог, админ школы, админ города, админ области, глобальный админ.

## 8. Критерии входа в тестирование
- Требования согласованы.
- Сборка развёрнута на тестовой среде.
- Миграции применены.
- Тестовые данные подготовлены.
- Известные дефекты задокументированы.

## 9. Критерии выхода
- Все P0/P1 требования проверены.
- Критические и высокие дефекты закрыты.
- Регрессия пройдена.
- Нагрузочные цели достигнуты.
- Пентест без критичных уязвимостей.
- Отчёт о тестировании подписан.

## 10. Классификация дефектов
| Уровень | Описание | Срок исправления |
|---|---|---|
| Blocker | Невозможно использовать ключевую функцию | Немедленно |
| Critical | Потеря данных, утечка, обход прав | До релиза |
| High | Ключевая функция работает неверно | До релиза |
| Medium | Ошибка с обходным путём | В ближайшем спринте |
| Low | Косметика, неудобство | По плану |

## 11. Автоматизация
- Backend: pytest, httpx.AsyncClient, тестовая БД.
- Frontend: Vitest, React Testing Library, Playwright.
- Mobile: Flutter integration_test, Patrol.
- API: Schemathesis/контрактные тесты.
- Нагрузка: k6 или Locust.
- Безопасность: SAST, DAST, dependency scan.
- CI: тесты на каждый pull request.

## 12. Метрики качества
- Покрытие критичных сценариев автотестами ≥ 80%.
- Доля автоматизированной регрессии ≥ 60%.
- Дефекты на релиз и динамика.
- Время исправления.
- Доступность и latency.
- Доля успешных AI-проверок с ручной валидацией.

## 13. Отчётность
- Ежедневный статус в трекере.
- Отчёт о тестировании по шаблону ШК-10-02.
- Реестр дефектов.
- Матрица покрытия требований.
- Итоговый акт испытаний.

## Проверки веб-клиента

- `npm run typecheck` — обязательная проверка TypeScript strict.
- `npm run build` — проверка production-сборки Vite и Tailwind.
- Ручные сценарии: вход, дашборд, группы, карточка группы, сервисы,
  переключение активации, профиль, мобильное меню.
- Для пилота проверяется раздача `frontend/dist` через FastAPI.
- Автоматизированные E2E-тесты (Playwright) — следующий шаг.
