## 1. Объект испытаний

- четыре сервиса ступеней: `primary_education`, `secondary_education`,
  `vocational_education`, `higher_education`;
- миграция `0004_education_levels`;
- API учреждений, групп, программ и академических профилей;
- миграция `0005_curricula`;
- API учебных планов, кредитов и компонентов;
- веб-экран `/education/{level}` и блок учебных планов;
- модули обучения по новым ступеням.

## 4. Локальная проверка API

Проверено на локальном backend с реальной пилотной БД:

- `GET /api/v1/education/primary/overview` — `200`, 4 класса;
- `GET /api/v1/education/secondary/overview` — `200`, 7 классов;
- `GET /api/v1/education/vocational/overview` — `403` при отключённом сервисе;
- после включения сервиса и создания тестового колледжа:
  - `POST /api/v1/org/schools` — `201`;
  - `POST /api/v1/education/vocational/programs` — `201`;
  - `POST /api/v1/education/vocational/profiles` — `201`;
  - `GET /api/v1/education/vocational/overview` — `200`, 1 обучающийся,
    1 программа;
  - `GET /api/v1/education/vocational/profiles` — `200`, 1 профиль.

Тестовые учреждение, пользователь, программа и профиль удалены после
проверки; активация сервиса восстановлена.

Для учебных планов проверены контрактные тесты OpenAPI и Pydantic, а также
применение миграции `0005_curricula` к пилотной PostgreSQL. Полная проверка
живых маршрутов `/curricula` будет выполнена после доставки нового backend на
пилотный сайт: на момент проверки после Restart живой OpenAPI всё ещё
содержал старую версию без маршрутов `/api/v1/education/*`.

## 5. Замечания

1. Пилотная школа пока не содержит учеников, оценок и посещаемости, поэтому
   численность в сводках равна нулю. Это ограничение данных, а не API.
2. В интерфейсе профессиональных ступеней реализованы управление программами
   и формы создания/редактирования профилей обучающихся и преподавателей.
   Выбор пользователя использует `/admin/users`; это соответствует текущим
   ролям `admin` и `superadmin`, у которых есть `profiles.manage`. При выдаче
   права неадминистративным ролям потребуется отдельный endpoint кандидатов.
3. Учебные планы и практика реализованы как компоненты плана. Сессии,
   зачётные ведомости, перевод кредитов, компетенции и договоры с
   предприятиями требуют отдельного этапа.
4. Новый код не доставлен на Alwaysdata: перезапуск пилота загрузил старые
   файлы. Требуется отдельная команда на деплой backend и frontend.

## 6. Вывод

Ступени образования реализованы как отдельные включаемые сервисы, миграции
`0004` и `0005` применены к пилотной PostgreSQL, API и веб-клиент проверены
на контрактном уровне. Следующий этап — доставка кода на пилот, наполнение
колледжа и вуза, затем зачётные ведомости, сессии и перевод кредитов.
